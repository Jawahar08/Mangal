## 2. THE PRODUCT VISION

MangalSutra is not a conventional matrimonial website.

A conventional matrimonial product often follows:

Profile → Like → Match → Chat → Marriage.

MangalSutra should support a broader journey:

Discover → Understand → Verify → Assess → Connect → Prepare → Marry → Nurture.

The long-term journey is:

Find a person → Understand each other → Verify important information → Prepare for marriage → Marry → Build a healthy family → Live well together → Grow together.

The core positioning is:

**MANGALSUTRA — More Than a Match. A Life Journey.**

Supporting concepts include:

- Marriage, With Trust.
- Find. Verify. Understand. Belong.
- AI-powered matchmaking.
- Vedic compatibility.
- Digital verification.
- Relationship intelligence.
- Spiritual wellbeing.

The product has four connected parts:

1. **MangalSutra:** Core matchmaking, profile management, discovery, compatibility, messaging, and relationship journeys.
2. **ChaanBean:** Trust and verification infrastructure, including evidence-backed verification workflows, consent management, protected documents, and verification statuses.
3. **Pratha:** Spirituality, rituals, meditation, wellness, and relationship guidance.
4. **MangalSutra Marketplace:** Future commerce for wedding services, wellbeing products, spiritual products, and couple experiences.

The platform should help people make informed relationship decisions and continue providing value after marriage.

Do not reduce the project to a generic dating application, a profile-card gallery, or a collection of unrelated dashboards.

## 3. NON-NEGOTIABLE DEVELOPMENT PRINCIPLES

### 3.1 UX-first development

Every feature must be designed around an actual user goal.

Before implementing a significant feature, understand:

- Who uses it.
- What problem it solves.
- When it becomes relevant.
- What information it needs.
- What the user sees before, during, and after the action.
- What happens when the action fails.
- What happens when information is missing.
- What the user can cancel, edit, skip, or undo.
- What personal information is exposed.
- How the experience works on mobile, tablet, and desktop.
- How usability and accessibility will be tested.

Do not create interfaces merely because a database table or API endpoint exists.

### 3.2 Inspect before changing

Before editing the repository:

- Inspect the complete project structure.
- Read the package manifest and dependency versions.
- Inspect routing and application entry points.
- Inspect existing components and design patterns.
- Inspect authentication and authorization.
- Inspect database schemas and migrations.
- Inspect API endpoints, Edge Functions, and server-side logic.
- Inspect existing matching and compatibility implementations.
- Inspect AI integrations.
- Inspect verification integrations.
- Inspect tests, lint configuration, and build scripts.
- Inspect existing responsive layouts and accessibility.
- Identify unfinished features, duplicated logic, security issues, and broken flows.

Do not assume the written specification accurately describes the current implementation. Verify everything against the code.

If the MangalSutra Web/App PDF is available, read it completely, including diagrams, tables, page-specific requirements, and the later sections. Preserve the original requirements and distinguish them from your recommendations.

### 3.3 Preserve the existing technology stack

The project documentation describes an existing foundation using:

- React.
- TypeScript.
- Vite.
- Supabase and PostgreSQL.
- Edge Functions.
- Gemini AI.
- Firebase Cloud Messaging.
- Capacitor for Android.

Confirm which technologies and versions are actually present.

Reuse existing working architecture wherever practical. Do not migrate frameworks, replace the database, introduce another backend, or rewrite functioning modules without a clear technical justification.

If the existing repository uses a different or newer configuration, report the difference and recommend the least disruptive approach.

### 3.4 No fabricated capabilities

Never pretend that a third-party API, government integration, verification provider, database record, or feature exists when it does not.

Use clear distinctions between:

- Implemented and tested.
- Implemented but not verified.
- Partially implemented.
- Mocked or simulated.
- Planned.
- Blocked by provider access, credentials, authorization, or external dependencies.

Never present mock verification results as real verification.

Never fabricate astrology results, compatibility calculations, identity verification results, court-record findings, police checks, or AI evidence.

### 3.5 Maintainability

Use modular architecture, reusable components, clear types, validated data contracts, documented business rules, automated tests, and incremental migrations.

Avoid monolithic components, duplicated business logic, unnecessary dependencies, hardcoded production data, insecure client-side authorization, and placeholder buttons that appear functional but do nothing.

### 3.6 Work in controlled phases

Do not attempt to implement the entire ecosystem in one enormous change.

Maintain a complete long-term feature inventory while delivering a small, testable, coherent first release.

Do not remove a future feature from the product vision simply because it is not part of Phase 1.

## 11. IMPLEMENTATION RULES AFTER THE AUDIT

Once the audit and first implementation plan are complete, proceed incrementally.

For each feature:

1. Confirm its purpose and scope.
2. Identify the user journey.
3. Identify existing code to reuse.
4. Define UI states and acceptance criteria.
5. Implement the smallest complete vertical slice.
6. Connect real backend functionality where available.
7. Validate permissions and sensitive-data handling.
8. Test responsive behavior and accessibility.
9. Run appropriate automated tests.
10. Verify the production build.
11. Report files changed and any unresolved limitations.

Do not stop at static mockups unless the current task explicitly requests a prototype.

Do not connect fake data to a UI that claims to display real verification results.

Do not use placeholder links, inert buttons, unimplemented form submissions, or fake success messages.

Do not silently replace working implementations.

Use small, reviewable changes and explain consequential architecture decisions.
